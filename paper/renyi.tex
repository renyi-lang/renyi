\begin{abstract}
AI agents write and run small programs that glue services together.
The person who runs such a program wants to know what it can touch
before it runs and what it did after, and a script in a general-purpose
language answers neither. Renyi is a statically typed scripting language
whose signatures declare effects as scoped, budgeted capabilities. The
checker refuses a function that uses what it does not declare, the
grant of \texttt{main} is the whole program's authority, dependencies
included, and at run time every effect passes one boundary in the
virtual machine where the grant, the budgets and the provenance guards
are checked. The same boundary makes a run recordable as data, replayed
offline, narrated through the program's own \texttt{purpose} clauses and
reproduced on another machine from its manifest. The surface syntax is a
regular subset of English with one spelling per concept, named
arguments, no exceptions and a fix in every diagnostic, and its rules
were chosen by measuring language models reading and writing it. Three
statements hold of the rules and are mechanized in Lean 4. The declared
authority bounds every effect, a guarded value leaves only through its
sinks, and a replay of a recording makes the same calls with the same
answers. On AgentDojo's 629 security cases, 90.8\% of the injected goals
need a capability, a scope or a count outside what the benign task's
program declares, so a program that passed review for the task cannot
carry them out. On the released toolchain every example workflow's
recording reproduces on another operating system, agents given only the
language's one-page skill file wrote four of five workflows clean within
two attempts, and Claude Sonnet 5.5 reading the cheat sheet alone
predicts the output of corpus programs at 90\% and explains them at
100\%.
\end{abstract}

\section{Introduction}

Language models now write programs on behalf of a person, a few dozen
lines that read files, call a web API, transform data and print or save
a result. The person does not read such a program the way a reviewer
reads a pull request. They skim it, run it, and look at the output.
Between the skim and the run stands the question of what the program is
able to do, to which paths, hosts and services, and how often. After
the run stands the question of what it did, and whether the person can
show someone, or run it again, and get the same answer.

In a general-purpose scripting language neither question has a cheap
answer. Any line of a Python or JavaScript program may open any file or
socket, an import may do so at load time, and a dependency update may
add a network call that nothing in the program's text reveals.
Sandboxes answer the first question from the outside, at the
granularity of a process (Deno's permission flags~\citep{deno},
containers, WebAssembly runtimes), and the second not at all. Effect
systems answer the first from the
inside~\citep{leijen2014koka,brachthauser2020effekt}, but their
languages were designed for other writers and readers, and they say
nothing about what a run did. The languages
designed for an agent's programs (Section~\ref{sec:related}) separate
the logic from the calls, for approval or for speed, and answer neither
question at the signature.

Renyi is designed around those two answers (Figure~\ref{fig:overview}).
Every function's signature lists what it needs, the checker refuses a
body that uses what its signature does not declare, directly or through
a call, and the signature of \texttt{main} is the whole program's grant,
which must cover every dependency it reaches. At run time every effect
passes one boundary in the VM, which is what makes a run recordable,
replayable and reproducible. The surface is a regular subset of English
that fits on one page of under 3,000 tokens, and its rules were chosen
by measuring language models reading and writing the language
(Section~\ref{sec:readability}). Section~\ref{sec:design} gives the
design, Section~\ref{sec:implementation} the implementation and
Section~\ref{sec:evaluation} the measures on the released toolchain,
among them the authority gap, how often an injected goal needs an
authority outside what the benign task's program declares, measured on
a benchmark of injection attacks before any model runs
(Section~\ref{sec:gap}).

\section{The design}
\label{sec:design}

\subsection{A program}

Figure~\ref{fig:program} shows a workflow from the toolchain's starter
pack, shortened. The first clause of \texttt{main} the reviewer reads is
its \texttt{needs}. The program prints to the console, reads its
arguments, and makes at most five HTTP requests per run to one host,
and nothing else can happen, whatever the rest of the file says.

\begin{figure}[tbp]
\begin{lstlisting}[basicstyle=\footnotesize\ttfamily]
module api_digest
  purpose: Fetch a repository's public numbers from the GitHub API and print a one-line digest.

import std.console
import std.environment
import std.http exposing Url, HttpError
import std.json exposing JsonError

public type DigestError is one of
  purpose: Why the digest could not be printed.
  Unreachable(detail: Text)
  BadResponse(detail: Text)
end

public function fetch_repository(name: Text)
  returns Repository
  or fails with HttpError or JsonError
  needs network.http("api.github.com")
  purpose: Download the record of the repository "owner/name".

  let response be http.get(Url("https://api.github.com/repos/{name}")) otherwise fail
  let repository: Repository be json.parse(response.body) otherwise fail
  return repository
end

public function main()
  or fails with DigestError
  needs console, environment, network.http("api.github.com") at most 5 per run
  purpose: Print the digest of the repository named by the argument, rust-lang/rust by default.

  let arguments be environment.arguments()
  let name be arguments.at(0) otherwise "rust-lang/rust"
  let repository be

      when success(found) then found
      when failure(error: HttpError) then fail with Unreachable(detail: error.to_text())
      when failure(error: JsonError) then fail with BadResponse(detail: error.to_text())
    end
  ...
end

\subsection{Four foundations}

Everything the following sections promise follows from four properties
of the language, each a decision taken before any tool was written.

\begin{enumerate}
\item \textbf{Effects are in the type system, with scopes.} A function
  without a \texttt{needs} clause is pure, and time and randomness are
  capabilities. The runtime therefore sees every effect at one
  boundary, which is what makes a run recordable, countable and
  taggable (Sections~\ref{sec:capabilities} and~\ref{sec:recording}).
\item \textbf{Every value is immutable and every binding owns its value.} A
  function is passed by name and captures nothing, a top-level binding
  is a constant, and a value reaches another only by being copied or
  moved into it. The value graph is acyclic, a race is unwritable, and a
  service's state lives outside the program (Sections~\ref{sec:memory}
  and~\ref{sec:live}).
\item \textbf{Definitions are content-addressed.} A definition's
  identity is the hash of its canonical form, so a rename changes
  nothing and a changed body changes everything that depends on it
  (Section~\ref{sec:identity}).
\item \textbf{Documentation is syntax.} Every module and every public
  definition carries a \texttt{purpose} line, so a run can be narrated
  and a definition retrieved in the words its author wrote.
\end{enumerate}

\subsection{Capabilities in signatures}
\label{sec:capabilities}

A \texttt{needs} clause lists capabilities. The kinds are those of the
standard library's primitives, \texttt{console}, \texttt{environment},
\texttt{time}, \texttt{random}, \texttt{filesystem.read},
\texttt{filesystem.write}, \texttt{network.http},
\texttt{network.socket}, \texttt{process}, \texttt{screen},
\texttt{foreign} and \texttt{python}. A capability may carry a
\emph{scope} (a path, a host, or a parameter of the function, so that a
library function can say \texttt{needs network.http(host)}), a
\emph{budget} (\texttt{at most $n$ per} second, minute, hour, day or run,
or \texttt{at most $n$ of} a parameter \texttt{per} unit, which sums
that argument in place of counting calls) and a \emph{guard}
(\texttt{only to} a sink, below).

Capabilities form a tree (\texttt{filesystem} covers
\texttt{filesystem.read}) and scopes an order. A path prefix contains
its sub-paths, a host, a variable or a program name contains only
itself, and a capability without a scope contains every scope. A
granted capability covers a needed one when its path is the needed
one's or an ancestor of it and its scope contains the needed scope. The
static rule is coverage under this order. A function's body may use,
directly or through a call, only capabilities its signature covers, a
test's head covers its body likewise, and the grant of \texttt{main}
must cover every function the program reaches, in its own files and in
its packages. The diagnostic names the callee, the capability and the
fix (\texttt{capability-missing}, \texttt{write `needs network.http`}).
Across a package boundary only the kind is checked statically, since a
library cannot know its caller's hosts, and the scope is left to the
run.

The dynamic rule is the grant stack. The effective grant of a running
function is the intersection of the program's grant with the scopes
declared along the call chain, and every primitive checks the actual
host or path against it at the moment of the call, so a general HTTP
client package that declares \texttt{network.http} without a scope
serves a program that grants one host. Every narrowing from outside the
program is the same intersection, \texttt{renyi run -{}-deny},
\texttt{-{}-allow-host} and \texttt{-{}-at-most}, and the embedding
API's sandbox, where a host loads a module under a grant narrower than
its own \texttt{main} declares, with a memory budget kept by a counting
allocator. Nothing from outside can widen a grant. A budget keeps a
counter per capability and scope, a sliding window of time stamps for a
unit of time and a plain count for the run.

A guard is a run-time taint of constant cost. The guards of a run are
the capabilities of the grant that carry \texttt{only to}, at most 64,
each a bit of the one-word origin every value carries. A primitive call
under a guarded capability tags its result with the bits of the guards
that cover it and with its arguments' origins, and every operation of
the VM tags its result with the union of its operands'. Before an
outgoing primitive call the boundary requires every guard set in the
arguments' origins to name a sink that covers the call; otherwise the
call fails with \texttt{Guarded(origin, sink)} before anything leaves.
A recording stores plain values and spells the guards in its grant
header, so a replay derives the same origins. Guards track explicit
flow only (Section~\ref{sec:limits}).

\subsection{Packages}

A package's effect manifest is computed by the tool from its sources.
\texttt{renyi index} derives every public function's transitive effects
and failure types, and the client recomputes them on every fetch and
refuses a package whose claimed manifest differs from the computed one.
\texttt{renyi add} prints the effects a dependency brings before
anything is written; \texttt{renyi update} diffs the manifests of the
old and the new version and refuses one whose effects widen unless
\texttt{-{}-accept-effects} is given and \texttt{main} covers the new
capability; the lockfile pins content hashes, so a republished version
with new effects is a different hash and a refused update.
\texttt{renyi audit} lists every locked dependency's transitive effects
against the program's grant. A package that calls native code needs
\texttt{foreign}, and a program that grants it is told so the first
time it runs.

\subsection{Recording, replay, narration, reproduction}
\label{sec:recording}

A Renyi run is a function of its code, its dependencies and the
sequence of answers its primitive calls received, because everything
outside the primitive calls is pure. There is no ambient I/O, no
reflection and no foreign call without a capability; time and
randomness are capabilities, answered at the boundary like any other;
maps and sets iterate in insertion order; decimal and float arithmetic
follow their standards; and tasks run one after the other, so the order
of their calls is the order of the text. A recording is therefore an
oracle for the run, and a replay checks that the same code with the
same answers gives the same output.

\texttt{renyi record} writes a run as a JSON document, one entry per
primitive call with its arguments and its outcome, and \texttt{renyi run
-{}-replay} answers every primitive call from it, touching nothing
outside the process. A call is matched by primitive and arguments first
and by sequence only when several entries match, and before the first
call the recording's grant must be covered by the grant it is replayed
under, so a recording cannot bring an effect past a test's
\texttt{needs}. Arguments and outcomes are encoded by the library's JSON
rules, so a recording is readable and editable by a person or an agent,
and a replay decodes it against the program's declared types, so a
response whose shape no longer fits fails the replay as it would fail in
production. A recording can be redacted by name (a header, a field) and
keeps a placeholder with the hash of what was removed.

The manifest in the recording's header names everything the run
depended on, the toolchain, the content hash of \texttt{main}'s closure,
every dependency's version and hash, the grant, the arguments, the
outcome and the hash of the output. \texttt{renyi reproduce} refuses a
program whose \texttt{main} does not hash as the manifest says, warns
when the toolchain differs, refuses when the dependencies differ,
replays, and compares the outcome and the output; a difference names the
first call that differed. A \texttt{replays} test pins a function with
effects to a recording the same way, and \texttt{-{}-refresh} records it
live once.

\subsection{Three statements}
\label{sec:statements}

The rules of this section keep three properties, proved on paper in the
repository's \texttt{docs/research/}\allowbreak\texttt{core-calculus.md} over an abstract
machine whose steps are pure steps and primitive calls, and mechanized
in Lean 4 (the repository's \texttt{formal/}, Lean core alone, built by
the continuous integration with no \texttt{sorry}). Coverage and the
grant stack are those of Section~\ref{sec:capabilities}, and a
primitive call is admitted only when the innermost grant covers its
effect.

\textbf{Theorem 1 (authority bound).} In every run of a program the
checker accepts, every effect that happens is covered by the run's
grant, \texttt{main}'s \texttt{needs} narrowed by the host, and its kind
by \texttt{main}'s \texttt{needs}; within one checked program a
primitive is refused on its scope alone, its kind being covered along
the whole chain.

\textbf{Theorem 2 (guards admit only their sinks).} A value's origins
are exactly its explicit provenance, the guards whose data it was
computed from through the operations of the VM, and every primitive
call that happens has, for every guard in its arguments' provenance, a
sink covering its effect. Implicit flow is outside the statement.

\textbf{Theorem 3 (replay).} The replay of a recording of a run makes
the same primitive calls with the same answers and produces the same
output, by induction on the steps, since every pure step is a function
of the state and the recording answers every primitive call as the
world did.

Each proof names what it rests on, the assumptions of
Section~\ref{sec:recording} with no observable identity and budgets
and guards decided by the state. Each is a sentence of the reference,
and a change to one is a change to the statement. The Lean models are one
machine per theorem, frames with grants for the first, values carrying
their origins for the second, an abstract state with pure steps as a
function for the third, whose replay starts from the live run's initial
state, the one place the model asks more than the statement.

\subsection{The surface}

The grammar is a W3C EBNF of 228 lines, frozen by decision and held
equal to the parser by a test that interprets it over the corpus. Its
rules for the two readers:

\begin{itemize}
\item \textbf{One spelling per concept.} \texttt{let $x$ be $e$};
  \texttt{change $x$ to $e$} is the only mutation; \texttt{is} and
  \texttt{is not} are the only equality; blocks end with \texttt{end} and
  indentation means nothing; the formatter has one canonical layout.
\item \textbf{Names that read.} Values and functions in lower snake case
  of at least two characters; 88 reserved words that include the query
  vocabulary (\texttt{for each item in items where \ldots\ sorted by
  \ldots\ collect}, \texttt{sum}, \texttt{count}, \texttt{group by}),
  so that a loop reads as the sentence it is.
\item \textbf{Calls that name their arguments.} One argument is
  positional; two or more are all named, in declaration order. A
  function passed as a value is passed by its name.
\item \textbf{Failure in the signature.} A function that can fail says
  \texttt{or fails with $E$}; a call that can fail or answer
  \texttt{nothing} takes \texttt{otherwise} on the same line
  (\texttt{otherwise fail}, \texttt{otherwise $d$}, \texttt{otherwise
  return}, \texttt{otherwise continue}, \texttt{otherwise crash with
  "reason"}). There are no exceptions.
\item \textbf{Nothing unused.} Every binding is read, every result is
  used or \texttt{ignore}d, a name is bound once per scope.
\item \textbf{Prose in the syntax.} Every module and every public
  definition carries a \texttt{purpose} line; \texttt{example} lines on
  pure functions are tests; \texttt{tags} and \texttt{see also} are
  retrievable metadata.
\end{itemize}

Every rule is a diagnostic with a code and a fix. The reference lists
114 codes, and the lexer, the parser and the checker take the fix as an
argument of every diagnostic they raise, so none can be added without
one.

\subsection{The edges of the guarantees}
\label{sec:limits}

Each guarantee stops somewhere. Guards stop the wholesale exfiltration
a prompt injection aims at, not a covert channel; implicit flow, timing
and the size of what is sent are not tracked, so a program can leak one
bit per run through a branch, and the budget on the sink is what bounds
the rate. A path scope contains a path by its text, with nothing
resolved on disk, so a symbolic link under a scope reaches wherever it
points. What a \texttt{foreign} or a \texttt{python} function does, once
granted, is outside every guarantee of the VM, which is why both are
capabilities a reviewer reads in the grant. The sandbox isolates
effects, time and memory; it does not hide timing or scheduling from
the module, and the module's console output goes to the process's
streams. A recording holds what the primitives answered, not what the
world would answer today, so \texttt{reproduce} shows that the program
still computes the same output from the same answers, not that the
answers are still true.

\section{The implementation}
\label{sec:implementation}

\subsection{The toolchain}

The toolchain is one binary, \texttt{renyi}, written in Rust in ten
crates (103,194 lines at release 0.4.0), with the checker, the packages,
the project map, the workspace a language server and an MCP server keep
between calls, the VM, the sandbox API, a WebAssembly build and a C API
with a Python binding. The standard library is 16 modules declared in
Renyi (795 lines of declarations compiled into the checker) with native
implementations in the VM. The language is specified by a reference of
one section per construct with the grammar excerpt, the static rules
with their codes and the run-time behaviour, and a conformance suite of
67 cases (programs, commands, expected outputs, exit codes and
diagnostic codes) runs against any \texttt{renyi} binary without the
Rust crates, on Linux and Windows for every push.

\subsection{The virtual machine}

The checked tree is lowered to a stack bytecode, every operation
annotated with the type the checker inferred for its expression. The VM
runs it on three tiers. The interpreter runs every program first. A
\emph{template tier} assembles, at a code object's first call, a fixed
machine-code sequence per operation over the interpreter's helpers,
with every value boxed in the interpreter's layout, and counts the
operations it runs. A code object that has run a fixed factor times its
size is promoted to the \emph{optimising tier}, which translates it to
Cranelift IR~\citep{cranelift} on a background thread, or at a loop
header with on-stack replacement. An abstract interpretation first
settles which operands and locals stay unboxed in registers, which
calls borrow their arguments where they lie, which field reads and
record updates are done in place, and which calls push no frame
record. A hand-back rebuilds the interpreter's state at any point the
generated code cannot continue.

The primitive boundary is one function, \texttt{call\_native}, through
which every effect passes. It checks the effective grant and the
budgets, records or replays the call, and narrates it. Both machine-code
tiers call the library's hot pure primitives (text, list, map and number
operations) through in-place entries that bypass the boundary, and an
effect passes it from every tier.

\texttt{renyi build} writes an \emph{image}, the bytecode in a binary
encoding with the machine code of every function, mapped executable from
the file at a 16 KB alignment where the system allows; \texttt{build
--exe} appends the image to the binary itself as a self-contained
executable. \texttt{renyi run} keeps two caches, the image of a program
it compiled machine code for and the compiled program keyed by the
content hashes of every file the front end read.

\subsection{Memory}
\label{sec:memory}

The value graph of a Renyi program is acyclic, since a value is
immutable and reaches another only by copy or move, so the VM counts
references without a tracing collector. A value is freed when its count
reaches zero, so a file or a connection closes as soon as it is dropped
and there are no pauses; a value whose count is one is updated in
place, so that \texttt{change items to items.append(item)} is a
constant-time append when nothing else holds the list; and the compiler
marks the last read of every local as a move, so an argument is handed
over rather than copied. This is the model of
Perceus~\citep{reinking2021perceus}, with the acyclicity given by the
language rather than assumed. Because the checked tree carries the
types, the emitters turn a \texttt{with} on a uniquely held record into
an update of the block where it lies, and the generated code raises and
lowers the counts in place. The language and its diagnostics speak of
values only; ownership and lifetimes stay inside the VM.

\subsection{The toolchain in the browser}

The front end, the checker and the interpreter build for
\texttt{wasm32-unknown-unknown} as a module with a C ABI of sixteen
exports, 3,062,776 bytes (995,913 gzipped) at release 0.4.0. A run that
presents a frame through \texttt{std.screen} suspends in the VM and is
resumed by the page with the keys held and the time elapsed, which is
how the project's demonstration game, a Doom-style raycaster of 2,814
lines of Renyi in sixteen modules, plays on the project's site; the
same program plays at the terminal under \texttt{renyi run}, where the
frames are drawn as text. In a headless Chrome on the first author's
machine it ran at 55 to 60 frames a second with 3.0 to 3.8 ms a frame
spent in the interpreted VM (2026-10-13).

\subsection{The compiler written in Renyi}

The lexer, the parser, the checker and the bytecode emitter are written
again in Renyi, 25,974 lines in the repository's \texttt{compiler/}
directory, run by the Rust VM. Three judges in the test suite hold them
equal to the Rust toolchain. The Renyi parser must print, byte for byte,
what \texttt{renyi parse -{}-json} prints on every program of the
corpus, the conformance suite, the compiler and the library; the Renyi
checker must print what \texttt{renyi check -{}-json} prints, with and
without \texttt{-{}-strict}, and exit as it exits, on every program
including the rejected ones; the Renyi compiler must write the bytecode
file \texttt{renyi compile} writes, and must write that file of itself.
Every diagnostic of the Rust front end is therefore also a diagnostic of
the Renyi one, kept in step by the judges on every commit.

The compiler is also the toolchain's speed measure. The gate for
switching the binary's front end to it was three times the Rust front
end's instructions on checking the compiler's largest module; the VM's
rounds and two rounds of cuts in the compiler's sources brought the
ratio to 2.96, and the Rust front end stays in the binary with the
Renyi one as the judged twin.

\subsection{Tooling}
\label{sec:identity}

Every definition is content-addressed, after Unison~\citep{unison}. Its
identity is the SHA-256 of its canonical text with its own name replaced
by a placeholder, every name that refers to another definition of the
project replaced by that definition's hash, and the library definitions
it uses appended with the library's version; definitions that depend on
each other are hashed as one component. A rename changes no hash, and a
changed body changes the hash of everything that depends on it. The
same hash is the code hash of the run manifest and the identity of
every record of the map, by which the semantic diff tells a rename from
a change.

\texttt{renyi index} builds the map from the checked program, for every
module and definition the signature, the effects, the failure types,
the callers and callees, the size metrics, the content hash and the
budgets. \texttt{index -{}-diff} compares two maps or a map and a
revision and lists the changes per definition with what each reaches
and the version bump it forces. \texttt{index -{}-chunks} writes the map
as JSON Lines, one chunk per module and definition with the hash of its
text as its id, so that a host's retrieval index is a projection of the
map that changes exactly when a definition does (three chunk texts were
measured against 45 questions with two embedding models and a BM25
baseline before the format was fixed). \texttt{renyi mcp} serves the
map, the checker, the formatter, the tests, the chunks and the cheat
sheet to an agent host over standard input and output, keeping the
checked world of the directory between calls. \texttt{renyi lsp}
serves editors from the same world, with a rename refused when the
project checked with the edits applied gains an error.

\subsection{Checked live update}
\label{sec:live}

\texttt{renyi serve -{}-watch} runs a service and, when a file of its
project changes, compiles the program again, checks the whole of it and
runs \texttt{main} again on the new version between two requests, with
the listening socket handed over, so a request that arrives meanwhile
waits and is answered by the new version. There is nothing to migrate,
because a module has no mutable state at the top level and no mutable
value escapes a function, so the state of a service lives in its
database, its files and its requests, and running \texttt{main} again
is the swap. The reload's message is the semantic
diff, the definitions that changed and any signature among them; a
version with errors is reported and the last good one keeps serving.
This is Erlang's hot code loading~\citep{armstrong2003} without its
hard part, a replacement on a running stack, and with the whole program
type-checked before it serves.

\subsection{The authority gap}
\label{sec:gap}

Theorem 1 says what a program cannot do; the question for an agent's
program is how much of what an attacker wants falls outside it. A prompt
injection reaches the program through the data a tool returns and asks
for something the user did not; in Renyi the program's authority was
declared and reviewed before the run, so the injected goal is carried
out only if it fits inside that authority. The \emph{authority gap} of
a benchmark is the fraction of its attacks that do not fit the smallest
grant the benign task's program can declare. It is a property of the
task and the attack, not of any model. For every pair in the gap, no
program that passed review for the task can carry out the attack,
whatever the model does once it runs, so the gap is the ceiling of
every defense that fixes authority before the run, and it says what is
left for the mechanisms that act during it.

We measured it on AgentDojo~\citep{debenedetti2024agentdojo}, the
benchmark of injection attacks on tool-using agents that
Quasar~\citep{mell2025quasar} and CaMeL~\citep{debenedetti2025camel}
are evaluated on, in its \texttt{v1} suites (banking, slack, travel,
workspace), 97 user tasks and 27 injection tasks, every user task of a
suite paired with every injection task of it, 629 pairs. Each task
declares a ground truth, the tool calls with their arguments that carry
it out, and the task files were parsed as syntax trees, which is all
the measure runs of them. A tool is a capability kind and the argument
naming a recipient, a URL, a channel, a hotel, a file or a participant
list is its scope. The user task's grant is what its program can write
in the \texttt{needs} of \texttt{main}: every kind its ground truth
calls; a scope for a kind when every call's scope is a literal the
user's prompt spells out (a recipient read from a file is not
declarable, and the kind is granted without a scope); \texttt{at most
$n$ per run}, $n$ the ground truth's count; and \texttt{at most $A$ of
amount per run} on a kind whose amount is a literal the prompt spells
out in every call, $A$ their sum. A pair is blocked when the
injection's calls need a kind the grant lacks, a scope outside a
declared one, more calls than the count or amounts summing past the
budget. Table~\ref{tab:gap} gives the result under five grants, from
the kinds alone to the ceiling of every literal as a scope.

The 35 pairs that fit the fourth grant are of two kinds. In 11 the
task's own sink is the attack's: a banking task names the attacker's
account as the user's new landlord, one asks for a password change and
the attack asks for another password, four slack tasks message Alice
and the attack sends Alice a link. In 24 the task itself reads its sink
from the attacker's data, a bill's recipient, a page's address found in
a channel, people found by name, a file found by listing, or calendar
events, which have no scope. No authority fixed before the run can
separate those, by construction. What acts on them is the recording and
the narration after the run, and the reviewer who sees
\texttt{send\_money} without a scope and knows the bill chooses the
recipient. The attacks that move as much money as possible are what a
budget on an amount is for; Renyi's budgets counted calls when the
measure was first made, the amount budget was added since, and in the
fourth grant it blocks one pair, the only task whose prompt spells the
amount. The attacks that remain under any limit send 0.01 with the
user's data in the subject. The measure assumes a program fixed before
any effect, uses the ground truth as the task's authority (the kinds
row is the floor, the ceiling row the bound a broader review could
reach), and runs no model, so it says nothing about utility, which
CaMeL reports with a model in the loop. The data, the scripts and the
pinned output are in the repository, held by its continuous
integration.

A model in the loop, on the same pairs, gives the same number. Claude
Sonnet 5.5, given the toolchain's skill sheet and cheat sheet, wrote a
Renyi program for each of the 97 user tasks against the suite's tools
bound as Python modules, one capability kind each, with at most three
attempts and \texttt{renyi check}'s diagnostics fed back. 96 tasks got
a program the checker accepts (55 at the first attempt, 38 at the
second, 3 at the third); 75 of them call exactly the ground truth's
tools, 13 call one it does not, and 14 miss one it calls, among them
the tasks whose actions are in the email or the web page the program
reads, which a program fixed before the run does not follow. Under the
grants those programs declare, 522 of their 622 pairs are blocked
(83.9\%), against 518 (83.3\%) under the ground truth's kinds on the
same pairs. The declared grant is the call set, so what the model
declares is what the ground truth declares, and the floor holds with a
model in the loop.

Run against the benchmark's own environments through the Python bridge
and judged by each task's own check, 54 of the 96 programs do their
task (56\%; 48 of the 75 whose call set is the ground truth's, 6 of the
21 others), each a program written once from the prompt and the
declarations without a look at the data. With the loop the toolchain
is built for (the program run under \texttt{renyi record}, the model
reading the run and the recording and writing the program again, each
version checked before it runs, at most two turns), 81 of the 96 do
their task (84\%), 27 repaired and none broken. The grant changed in 9
programs, widened in 5, four of them by a tool the ground truth calls,
and 520 of the 622 pairs are blocked under the final grants (83.6\%)
against 522 under the first, so the look at the data that repairs the
program does not loosen the grant. The sample, its programs, their runs
and the pinned reports are in the repository.

\subsection{Readability}
\label{sec:readability}

The surface syntax was measured before it was frozen by a protocol of
four tasks over the thirty programs of the corpus, with the one-page
cheat sheet as the model's whole knowledge of the language. \emph{Predict}
the output of a program; \emph{Explain} a program (graded by a second
model against the first author's description of its purpose, inputs,
outputs, effects and failures); \emph{Complete} a program with one
function removed (judged by the checker and the program's tests); and
\emph{Write} a program for a task not in the corpus (judged the same
way). Five samples per prompt; an item passes when four of five samples
pass; the thresholds are 90\% for Predict and Explain, 80\% for Complete
and 70\% for Write.

Four rounds were run in October 2026, each after a set of changes to
the grammar or the cheat sheet chosen from the previous round's
failures. The last, on Claude Sonnet 5.5 through its command-line
interface with no tools and the cheat sheet as the only system text
(345 samples), passed Predict at 90\% (9 of 10) and Explain at 100\% (30
of 30), and missed Complete at 79\% (15 of 19) and Write at 40\% (4 of
10). The changes the rounds forced are now the language's rules, that
one argument is positional and two or more always named (the largest
source of errors in the earlier rounds, 43 checker lines in round two,
none after), the parameter names of every library method on the cheat
sheet, and the \texttt{otherwise} that stays on the line of the value it
guards. The Write failures that remain are mostly the checker's
strictness on a long program (an unused binding, a guard the checker
proves superfluous), which the design accepts, since a program that
checks clean is one a reviewer can trust and the fix is in the
diagnostic.

\section{Related work}
\label{sec:related}

\paragraph{Languages for agents.} Three recent languages start from the
premise Renyi starts from, that an agent's program should separate its
logic from its effects, and take it elsewhere; Renyi's design, in
October 2026, was made without knowledge of them.
Quasar~\citep{mell2025quasar} annotates external calls with the
resources they touch and uses the annotations at run time to batch the
user's approvals and to run the calls in parallel; the program is
transpiled from a subset of Python, and the transpiler's is the only
static check. Pel~\citep{mohammadi2025pel} restricts what a model can
write at the grammar, by constrained decoding, so that a host forbids a
feature by removing it from the grammar. Composable effect
handling~\citep{wang2025effect} puts an LLM script's calls behind
handlers in Python, for parallelism and for a replay handler in tests.
CaMeL~\citep{debenedetti2025camel} is a defense rather than a language,
a Python interpreter that attaches capabilities to data values and
checks policies at every tool call, with a model in the loop, and it
reports utility and security on AgentDojo. Renyi puts the declaration
in the signature, checks coverage before the run across the program
and its packages, enforces scopes, budgets and guards at one boundary
and records what passed it; its measures are the reviewer's reading,
the agent's first attempt and the authority gap of
Section~\ref{sec:gap} rather than a benchmark's latency.

\paragraph{Capabilities.} The object-capability discipline of
E~\citep{miller2006robust} makes authority flow only along references;
Wyvern's module system~\citep{melicher2017capability} brings it to
modules, so that a module's authority is what it is handed; Pony's
reference capabilities~\citep{clebsch2015deny} serve data-race freedom.
Renyi's capabilities are coarser and closer to the program's text, a
named kind with a scope in a signature, enforced by the checker across a
program and its packages and by a grant stack at one boundary. Deno's
permission flags~\citep{deno} enforce the same kinds at the process
boundary, from the outside; Renyi puts them in the signature so that a
reviewer reads them and a package cannot hide them.

\paragraph{Effect systems.} Koka~\citep{leijen2014koka} and
Effekt~\citep{brachthauser2020effekt} type effects, Effekt explicitly as
capabilities a computation requires from its context. Renyi's effect
types are monomorphic and effects happen only at the boundary; the
design trades handlers for a signature a person reads in one pass and a
single run-time boundary that records what happens.

\paragraph{Record and replay.} rr~\citep{ocallahan2017rr} records a
process at the system-call boundary on stock hardware. Renyi's recording
is at the language's primitive boundary, typed by the program's own
declarations, readable and editable as JSON, and carries a manifest that
names the code, the dependencies and the grant, which is what
\texttt{renyi reproduce} checks.

\paragraph{Memory, identity and live update.}
Perceus~\citep{reinking2021perceus} gives Koka precise reference
counting with reuse in place; Renyi adopts the model and gets the
absence of cycles from immutable values without references.
Unison~\citep{unison} identifies a definition by the hash of its
syntax tree and makes names metadata; Renyi hashes canonical text with
references replaced by hashes and uses the identity for the manifest
and the diff rather than for a codebase store. Erlang~\citep{armstrong2003}
loads code into a running system and keeps two versions of a module
alive; Renyi's reload runs \texttt{main} again on a checked program
between two requests, since a service has no state to carry across.

\paragraph{Scripting and embedding.} Lua~\citep{ierusalimschy1996lua}
set the pattern of a small language embedded by a host that chooses
what to expose; Renyi's embedding API follows it with the grant as the
host's choice, enforced in the language rather than by what the host
registers.

\paragraph{Language models writing programs.} Codex and
HumanEval~\citep{chen2021codex} measure functional correctness of
generated Python; ReAct~\citep{yao2023react} and
Toolformer~\citep{schick2023toolformer} have models act through tools.
Renyi's readability protocol measures a model reading and writing a
language from one page, and its first-run measure an agent's loop with
the checker; the Model Context Protocol~\citep{mcp} is how the toolchain
reaches the agent.

\section{How this work was done}

AI was used for the code and the text, within the framework and the
instructions the authors set by hand.

\section{Conclusion}

Renyi answers what a person asks of a program an agent wrote. What it
can touch, the signature of \texttt{main} states and the checker and
the VM enforce, dependencies included. What it did, a recording states
as data and a manifest makes reproducible. The syntax that carries
those answers was chosen by measuring the readers it is for. The
toolchain is released and the language is self-hosted and judged; the
measures to follow are review time by people and the first-run rate
with the MCP server connected.

\paragraph{Availability.} The toolchain, the specification, the corpus,
the conformance suite, the readability harness and every measure's lane
are at \url{https://github.com/renyi-lang/renyi} under the Apache 2.0 license;
the site with the playground and the demonstration game is at
\url{https://renyi-lang.org}.
